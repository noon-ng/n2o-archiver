# N2O Archiver architecture

A macOS archive extractor written in Objective-C with a programmatic AppKit UI.
Each archive gets a window controller that displays an extraction job; the job
asks the plugin manager for an extractor and runs it off the main thread. Zip,
RAR, tar and similar formats use the statically linked libarchive; 7z uses the
bundled `7zz`.

## Components and where they run

![Components of N2O Archiver and the threads they run on: Finder, the open panel and the menu call AppDelegate on the main thread; AppDelegate creates a window controller per archive; the window controller starts and cancels an extraction job; the job asks the plugin manager for an extractor and runs it on a global dispatch queue; the libarchive extractor calls libarchive and the 7z extractor calls NA7zzTool, which runs the bundled 7zz; both write into a hidden staging folder that NAQuarantine marks before it is renamed.](architecture.svg)

Walnut outlines run on the main thread, steel outlines on a global dispatch
queue. The window controller only displays a job: it starts and cancels one, and
reacts to its progress and completion handlers. The job has no AppKit
dependency, and owns the `NSProgress` it hands to the extractor — the extractor
updates it from its own threads and stops when it is cancelled, and the job
reads it from a 0.1 s main-queue timer. The extractor, `NAQuarantine`, the removal
of failed or cancelled output, the unwrap and the rename all run in one block on
the dispatch queue; only the final state is set on the main queue. `NA7zzTool`
reads `7zz`'s stdout and stderr while it runs, so 7z progress arrives on a file
handle queue before reaching the main queue.

## Which slice implements each feature

![A matrix of features against the components that implement them. Rows are features such as opening from Finder, picking an extractor, extracting an archive, cancelling, showing errors, loading plugins and building the app; columns are the macOS entry points, AppDelegate, the window controller, the extraction job, the plugin manager, the libarchive extractor, the 7z extractor with 7zz, and the build. Each cell names the methods and flags that do the work.](architecture-matrix.svg)

Each row is a feature; the line runs through every component it touches, and
each cell names the code that does the work. Walnut chips run on the main
thread, steel chips on the dispatch queue or inside `7zz`, and plain chips sit
outside the app's own code. A red chip is a known limitation and a dashed amber
chip a path no test covers; the [README](../README.md) lists both.

The figure is generated by [make-matrix-svg.py](make-matrix-svg.py), which holds
the data — edit it there and re-run it rather than editing the SVG.

Extraction runs in the app process. Moving it into a sandboxed XPC service is
planned for a later version.
